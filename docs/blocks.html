Block reference

Every block type Expanse ships.

Expanse 1.7.0 ships twenty block types. Each page covers what the block runs, an example to start from, every configuration key with its default, how to use it, and what happens when a node fails.

A block is a service described in YAML that the cluster schedules onto nodes and runs as a sandboxed systemd unit. Apply one with expanse ctl block apply -f <file>; add --dry-run to validate it first. Getting started walks through a first block, and Features covers scheduling, rolling updates and self-healing. On a node, expanse ctl catalog list lists the types and expanse ctl catalog show <type> prints a type's schema.

Fields every block shares

Every block has the same outer shape; only spec.config differs by type.

Field under specMeaning
typeThe catalog type, <category>/<name>: one of the types below.
replicasHow many replicas to run. Omit it for a daemonset.
strategy.kindUnset: active-active replicas. SINGLETON: exactly one instance, fenced by a Raft lease. DAEMONSET: one replica on every node.
strategy.updatemode (rolling or recreate), maxUnavailable, maxSurge and minReadySeconds.
resources.requestscpu and memory the scheduler reserves on the node. A VM uses them as its vCPUs and RAM.
storage[]Volumes: name, size, replication, mountPath, and filesystem: none for a raw device. A singleton with storage always runs where its volume's primary is.
placementantiAffinity: ANTI_AFFINITY_NODE keeps replicas on different nodes; requiredCapabilities such as [kvm] limits the nodes.
network.ports[]name, port, target_port, protocol, and expose: EXPOSE_VIP to put the port on the block's VIP, which forwards to target_port. Several ports share one VIP. The VIP holder binds the exposed port on its node, so a workload on that node must listen on a different target_port.
network.health_checkreadiness and liveness probes, PROBE_TCP or PROBE_HTTP. A port on a VIP needs a readiness probe; traffic skips a replica whose probe fails. A failing liveness probe restarts the replica, then moves it.
configThe type's own settings, checked against its schema. Each type's page lists them.

spec.secrets is refused until secrets can be stored and delivered.

Programs on the node

Most types run an upstream program, such as postgres or caddy, which the block's unit finds on the node's system profile. An installed node does not ship these programs: add the package to environment.systemPackages in the NixOS configuration (/persist/etc/nixos) of every node that may run the block, and rebuild. Only three types are built into Expanse.
